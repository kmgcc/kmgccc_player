# 产品文案与界面规范

这份规范适用于 kmgccc_player 的设置页、弹窗、面板、按钮和其他面向用户的原生界面。它与
AGENTS.md、CLAUDE.md 一起构成 Agent 的产品界面契约。

## 文案

### 信息密度

每一段文字只承担一个清晰作用：命名功能、说明状态、引导操作，或在必要时交代风险。能从
标题、图标、布局和系统行为自然理解的内容，不再补写一遍。

优先保留具体信息，删去解释性的铺垫、重复的副标题和对用户判断没有帮助的形容词。按钮
只写动作，状态只写事实，设置项只写功能名称；补充说明只有在影响理解或操作时才出现。

### 句式与语气

文案直接写核心事实，避免“不是……而是……”“不会……”“不要……”等反向解释，以及
“接下来”“值得注意”“简单来说”等模板化过渡。权限、删除确认、数据风险和确实不可用
的状态属于必要提示，可以用最短的事实句说明影响和下一步。

整体语气朴实、书面、自然，具有人文气息，偶尔保留适度的文学意蕴。表达尊重用户，不
自夸，不口语化，不使用实现细节替代用户能理解的名称。技术名词只有在确实帮助理解时
出现，并配合通俗的说明。

句子不追求全部切短。有关联的内容用自然的长句承接，避免把一项完整意思拆成许多零碎
小字。每次新增或修改文案，都应完整通读相关页面，并逐条确认删除后是否仍然影响理解。

### 分隔符与信息布局

界面文案禁止用 `·` 装饰性地拼接词组或句子；正式名称或固定术语本身包含时除外。遇到这种写法，
先确认点号后的内容是否提供独立且必要的信息。多余就删，不要只改成逗号或空格；确有用处时，
按信息关系重新安排层级，例如将标题与辅助说明分行，或改为独立字段、控件或分组，不把两段文字硬挤在一行。

## 视觉与交互

### 统一来源

颜色从 ThemeStore / SemanticPalette 获取，视图层不自行创建一套主题颜色。设置页和
设置页的字体、间距和控件尺寸沿用 Settings 共享组件；弹窗遵循 [弹窗标准](popup-standards.md)，
由 PopupKit 与 App 的主题适配层集中提供。

新增模式先寻找现有组件和调用链，再决定是否扩展设计系统。局部页面不复制一套相似
modifier，也不通过临时颜色、间距或形状掩盖共享组件的问题。

### 按钮和设置行

- App 内按钮统一使用胶囊形状，优先使用共享 ButtonStyle。
- 设置文字左对齐，Switch 和其他尾部控件右对齐。
- 设置行保持稳定的标题、补充信息、控件和操作区结构；长文本应通过布局和截断策略
  解决，不随意改变字体层级。
- 颜色、透明度和背景层级承担主要的视觉区分。描边、阴影和发光不作为常规层级手段；
  确有可读性或系统交互原因时，先记录例外并检查其他状态。

### 弹窗和面板

App-owned 弹窗使用 AppPopupFrame、AppPopupScrollRegion 和共享胶囊按钮。AppDialogFrame、
AppDialogHeader、AppDialogFooter、SettingsTaskDialog 与 AppDialogGlassButtonStyle 作为兼容适配层，
复用同一份 PopupKit 源码。标准参数来自 PopupLab 定稿预设，App 的语义色由 ThemeStore 注入。

共享按钮标准仅用于窗口右下角操作组与右上角关闭。面板内工具按钮保持各处紧凑字号与尺寸，
使用 AppPanelButtonStyle；删除、清除等操作仅将文字标红。全屏 quick panel 沿用嵌入设置的
原有布局和关闭控件，外层材质、明暗与文字配色跟随 MiniPlayer 已解析的外观状态。

外层采用一层玻璃材质，内容分组使用颜色和透明度区分。标题图标对齐首行实际字形；
关闭按钮与操作组的外边距以弹窗边缘计算。阅读和只读任务列表允许局部悬浮按钮，
表单与可操作列表使用固定操作区；长内容的上下边缘在到达首尾时恢复清晰。

简短确认和错误可使用系统 Alert / confirmationDialog。文件、权限和更新 UI 沿用系统或
组件宿主；popover 的背景、箭头和自动关闭由系统管理。大型编辑器保留多栏和所需尺寸，
完整设置页保留 NavigationSplitView。保存、取消、忙碌关闭策略和全屏路由由原有业务 owner 管理。

## 可持续修改

开始修改前先回答三个问题：

1. 当前视觉或文案规则的真正 owner 在哪里？
2. 哪些页面和调用点会受到影响？
3. 这次修改应当修复共享组件，还是确实需要新的组件？

发现同类问题时，优先修复共享组件并迁移调用点；允许进行必要的架构性重构，但必须保持
既有功能，明确受影响的页面和验证范围。修复一个页面后留下同样的局部实现，不算完成。

UI 任务的默认验收顺序是：源代码影响范围、轻量一致性检查；常规改动的 Debug build 由维护者手动执行，只有符合仓库重大工程变更标准时才允许 Agent 在最后集中 build-only 编译，
再按风险检查真实设置和弹窗路径。浅色、深色、禁用状态、长文案和破坏性操作属于需要
单独关注的状态。代码检查和编译通过不能替代真实界面验收。

## Agent 交付

Agent 不需要在每次任务中复述整份规范。交付时说明：

- 修改了哪个共享组件或页面；
- 影响了哪些调用路径；
- 已完成的构建、脚本或界面检查；
- 尚未验证的真实用户路径。

# 本地音乐资料库重构计划

本文是 kmgccc_player 新一代本地音乐资料库的产品与工程实施规格。它合并了多资料库存储、原位资料库、目录来源、播放列表同步、NCM 转换、竞品资料库调研和实际用户反馈形成的最终决策，供后续 Agent 分阶段实施和验收。

本文不是头脑风暴。除非维护者重新拍板，标记为“确定”的行为不得在实现阶段自行改变。局部实现遇到阻力时，应调整底层架构，不得用改变用户行为的方式绕开。

> - 状态：阶段 0–8 的可测试代码基础已落地；智能集合、真实 UI/切库/退出、NCM、大目录和托管兼容矩阵仍待运行验收与后续接续
> - 目标工作树：`feature/multi-library-storage`
> - 当前范围：本地资料库；MCP 与云端资料库仅保留边界

## 1. 目标与优先级

本轮只建设本地音乐资料库。未来仍计划支持 MCP 和云端音乐资料库（例如 Navidrome），但本轮不实现远程登录、远程 catalog、流媒体、同步、下载缓存或 MCP 工具。

当前优先级如下：

1. 修复资料库创建、切换、删除、导入、扫描和窗口生命周期中的真实故障。
2. 重点重构原位资料库，使文件来源、目录监听、播放列表绑定和重复识别可靠可维护。
3. 保持托管资料库现有行为和旧用户兼容，只修复明确缺陷，不借重构改变其存储语义。
4. 升级逻辑歌曲、物理位置、来源、播放列表成员、专辑和艺人模型。
5. 增加清晰的文件夹视图，但保持主侧边栏克制并延续现有 APP 的视觉语言。
6. 在本地架构中保留稳定命令、查询、身份和播放资源边界，为未来 MCP/Navidrome 接入留出位置，但不提前实现抽象空壳。

## 2. 已确定的产品原则

### 2.1 三类数据必须分层

- 音频文件及其内嵌标签是文件侧事实。
- 播放列表、播放历史、手动元数据、来源绑定、忽略项和用户选择是资料库权威数据。
- 专辑、艺人、文件夹、搜索、统计和其他浏览集合是可重建投影。

资料库不是纯临时索引。播放列表、歌词、用户封面、手动修正和播放历史不能随重建索引丢失。

### 2.2 标签轴与文件夹轴平行

歌曲可以通过所有歌曲、专辑、艺人、文件夹、播放列表和搜索进入。这些入口是同一批逻辑歌曲的不同视图，不各自拥有歌曲副本。

标签质量不足时，文件夹视图必须仍然可用。文件夹不能被专辑或播放列表模型吞并。

### 2.3 本地能力零网络可用

扫描、导入、浏览、搜索、播放、目录监听和播放列表同步不能依赖网络补全。

在线信息补全只是一层可取消增强：

- 不决定歌曲是否可播放；
- 不阻止创建弹窗关闭；
- 不阻止切换或关闭资料库；
- 不直接覆盖用户手动元数据；
- 失败后可单独重试。

### 2.4 两种本地资料库长期并存

- **原位资料库（referenced）**：音频留在用户目录，APP 保存授权、位置、索引和用户资料，并持续监听来源变化。未来新建资料库默认首推此模式。
- **托管资料库（managed）**：导入时复制音频到资料库内部。外部导入源之后的变化不影响资料库。旧用户和既有资料库必须继续可用。

一个资料库的模式在创建后固定。不得把远程音频或另一种本地存储模式伪装成当前模式的 locator。

### 2.5 用户操作必须可解释

每个导入、扫描、删除和绑定操作都应能回答：

- 操作目标是什么；
- 会新增或修改什么；
- 是否会改动原文件；
- 操作完成了多少；
- 哪些项目失败以及如何恢复。

不得再出现“导入到第一个播放列表”、并发导入静默返回空结果、点击一个来源却扫描全部来源等不可见规则。

## 3. 明确不做和不照搬的内容

本轮不做：

- MCP Server、MCP tool schema 或 Agent 权限界面；
- Navidrome/Subsonic 登录、远程 catalog 和流媒体播放；
- 云端与本地 Track 合并、播放列表双向同步和冲突处理；
- 默认自动移动、重命名或整理用户的原位文件；
- 用标题、艺人和时长相似就静默合并歌曲；
- 无条件按 `&`、`+`、`/` 拆分艺人名称；
- 为托管资料库增加外部目录持续监听；
- 重新开放未完成的资料库位置迁移功能。

竞品能力用于确定原则，不照搬其全部 UI。主侧边栏不增加大量动态集合、品质统计或失效项目入口。

## 4. 主导航与文件夹视图

### 4.1 主侧边栏保持现状

主侧边栏沿用当前主要导航和层次，只做以下变化：

1. **用户播放列表**改成可折叠分组，默认展开。
2. **原位资料库**增加一个“文件夹”入口。
3. 不在主侧边栏增加最近播放、最常播放、品质统计、失效项目、来源管理等大量入口。
4. 失效项目放在“设置 → 数据”中管理。
5. 来源重连、扫描状态和来源删除以文件夹视图与设置中的资料库详情为入口，不占用主侧边栏。

托管资料库不强行显示没有实际意义的外部文件夹树。它继续保持当前主导航；若未来需要展示导入来源历史，应另行设计，不能把资料库内部的 `Tracks/<UUID>` 暴露给用户。

### 4.2 用户播放列表折叠行为

播放列表分组需要满足：

- 分组标题显示“播放列表”和数量；
- 展开/折叠状态按资料库持久化；
- 当前选中播放列表在恢复窗口状态时可自动展开并保持可见；
- 标题区域保留新建播放列表入口；
- 文件正在拖向折叠分组时，悬停短暂延迟后自动展开；
- 拖到具体播放列表行时，行高亮并锁定该播放列表为导入目标；
- 拖到分组标题但没有具体目标时，不随机选择播放列表，可拒绝并给出提示，或明确进入新建播放列表流程。

### 4.3 文件夹视图的窗口内布局

文件夹视图采用清晰的双栏结构，而不是继续向侧边栏堆入口。

```text
┌───────────────────────────────┬──────────────────────────────────────────────┐
│ 文件夹与单独歌曲              │ 当前选择                                     │
│                               │                                              │
│ ▾ 来源：外置音乐              │ 文件夹标题 / 路径 / 状态 / 最后扫描           │
│   ▸ Classical                 │                                              │
│   ▾ Pop                       │ 关联播放列表                                  │
│      2025                     │ [通勤] [收藏]                 [+ 建立关联]    │
│                               │                                              │
│ ▾ 来源：Music                 │ 包含的歌曲                                    │
│                               │ 标题  艺人  专辑  格式  状态                  │
│ 单独添加的歌曲                │                                              │
└───────────────────────────────┴──────────────────────────────────────────────┘
```

左栏职责：

- 按来源显示真实目录层级；
- 支持来源根、子目录和“单独添加的歌曲”虚拟分组；
- 显示可用、离线、权限失效、正在扫描等轻量状态；
- 支持树状展开、折叠和路径搜索；
- 不把播放列表混入目录树；
- 同一文件属于重叠来源时，逻辑歌曲仍只有一条，文件夹视图可以在多个路径节点中引用它。

右栏职责：

- 展示当前目录、来源或单独歌曲分组的摘要；
- 在顶部清晰展示与哪些播放列表存在来源绑定；
- 支持建立或解除“文件夹 → 播放列表”绑定；
- 在下方显示当前选择包含的歌曲；
- 支持播放、加入队列、显示 Finder、重新扫描当前来源等操作；
- 解除播放列表绑定时不删除来源、不删除所有歌曲中的 Track，也不删除原文件。

当选择来源根时，右栏展示该来源的全部绑定和全部歌曲；选择子目录时，只展示该子树及其关联。若一个子目录位于已授权来源之内，可用来源 ID 加相对路径表示绑定，不必重复申请同一父目录权限。

### 4.4 视觉与交互要求

- 使用现有 APP 的语义颜色、材质、圆角、行高、封面和工具栏体系，不单独创造一套“文件管理器皮肤”。
- 目录树强调层级、选中和状态，不使用大量彩色徽章。
- 播放列表关系使用紧凑卡片或 token，连接关系应直接读懂，不需要用户理解数据库术语。
- 离线和权限问题采用克制状态行与明确动作，不弹出连续模态警告。
- 列表滚动、选择和展开状态稳定；扫描更新不能把用户当前选择重置到顶部。
- 大目录必须分页或虚拟化，不能在主线程一次生成全部行和封面。

## 5. 所有歌曲、来源和文件夹的定义

### 5.1 所有歌曲

“所有歌曲”表示当前资料库所有已经导入或仍被来源声明的逻辑歌曲。

- 将文件或目录导入任何播放列表时，歌曲同时进入所有歌曲。
- 同一歌曲被多个来源、目录或播放列表引用时，所有歌曲只显示一次。
- 来源暂时离线或权限失效时，来源声明仍存在，歌曲保留并标记不可用。
- 一次完整且成功的扫描确认某个文件真正消失后，才移除对应物理位置。
- 没有任何剩余位置的歌曲进入设置中的可恢复失效项目，不继续占用正常所有歌曲视图。

### 5.2 来源

来源是原位资料库中用户授权给 APP 的目录或单独文件，是权限、扫描和监听边界。它不是播放列表，也不是专辑。

来源列表不只包括创建资料库时选择的目录，还包括后续：

- 导入到所有歌曲的目录或文件；
- 导入到某个播放列表的目录或文件；
- 从 Finder 拖入播放列表的目录或文件。

### 5.3 文件夹

文件夹是来源目录中的层级投影。来源负责授权和监听，文件夹负责浏览与绑定范围。来源与文件夹必须在模型上分开，避免选择一个子目录就重复创建父来源的权限 owner。

## 6. 新建、打开、切换和删除资料库

### 6.1 普通新建流程

普通用户新建资料库按以下顺序进行：

1. 选择资料库模式。
2. 默认首推原位资料库，并清楚说明“音乐保留在原位置，APP 自动监听变化”。
3. 托管模式继续说明“导入后复制到资料库，原文件变化不影响播放”。
4. 必须明确选择资料库存储位置。
5. 可选选择一个或多个音乐目录/文件，也可以创建空资料库。
6. 展示最终摘要和完整目标路径。
7. 创建最小资料库、注册并激活。
8. 创建弹窗立即关闭；来源扫描、NCM 转换和信息补全进入后台任务。

新建资料库时没有已有播放列表，因此原位模式不显示“绑定到已有播放列表”。创建时仅提供：

- 只加入所有歌曲；
- 可选“为每个所选目录创建同名播放列表并绑定”；
- 多个目录也可由用户明确选择“创建一个新播放列表并统一绑定”，但不应作为默认行为。

默认行为是只加入所有歌曲，不自动制造播放列表。

### 6.2 创建位置规则

- 用户没有选择位置时不能创建。
- 只有选完位置后才能检查冲突。
- 冲突提示必须展示具体完整路径。
- 可选择打开已有资料库、重新选择位置，或明确另建一个资料库。
- 不得在未选择位置时显示“该位置已存在”。
- 不得静默创建编号目录。

### 6.3 系统兜底资料库

系统兜底与普通新建是两条独立流程：

- 删除当前资料库后，优先切换到其他可达资料库；
- 没有可达资料库时，在默认位置自动创建空资料库；
- 空资料库显示“没有歌曲待导入”；
- 主窗口不进入“没有音乐资料库”的正常运行状态；
- 默认位置已有有效资料库时直接打开；
- 默认位置损坏或不可写时进入明确恢复流程，不能显示空白窗口。

### 6.4 删除语义

必须区分：

- 从 APP 注册列表移除资料库；
- 删除资料库自身的数据目录；
- 从原位资料库移除来源；
- 从资料库移除歌曲；
- 将原位音频移到废纸篓。

删除原位资料库或来源不得删除外部音频。移动原文件到废纸篓只能是单独、明确、可确认的操作。

## 7. 统一导入语义

### 7.1 导入目标与元数据上下文分离

每次导入都形成显式上下文：

```text
LibraryImportContext
  libraryID
  sessionGeneration
  destination
  metadataContext
  sourceKind
  originSurface
```

`destination` 只允许：

- `libraryOnly`
- `playlist(playlistID)`

`metadataContext` 独立表示当前艺人或专辑页面可能提供的元数据预填。它不能暗中改变播放列表成员关系。

### 7.2 根据 UI 状态选择目标

公共导入入口包括：

- Toolbar 加号；
- 导入菜单或快捷键；
- 将 Finder 文件/目录拖到主窗口普通区域。

它们按触发瞬间的 UI 上下文选择目标：

| 当前上下文 | 导入目标 | 元数据语境 |
| --- | --- | --- |
| 某个播放列表详情 | 所有歌曲 + 该播放列表 | 无额外覆盖 |
| 某个艺人详情 | 仅所有歌曲 | 可预填当前艺人，但必须在导入摘要中可见 |
| 某个专辑详情 | 仅所有歌曲 | 可预填当前专辑身份，但必须在导入摘要中可见 |
| 首页、所有歌曲、艺人总览、专辑总览、播放列表总览、文件夹总览或其他未定义页面 | 仅所有歌曲 | 无额外覆盖 |

文件选择器打开后即捕获资料库 ID、session generation 和目标。用户在选择器打开期间切换页面，不能让目标悄悄变化。若资料库已经切换，旧请求应取消并给出说明，不能写入错误资料库。

### 7.3 Sidebar 播放列表拖放优先

将文件或目录拖到 Sidebar 中某个具体播放列表行时：

- 固定导入到该播放列表；
- 该行视觉高亮；
- 不读取当前内容页面选择；
- 原位模式下，目录注册为来源并建立该目录到播放列表的绑定；
- 托管模式下，目录执行一次性复制导入，不建立外部监听；
- 已存在歌曲只增加播放列表成员，不产生重复 Track。

若拖放位置同时位于窗口全局 drop zone 和播放列表行，播放列表行处理器优先，事件不得被执行两次。

### 7.4 原位与托管导入行为

原位模式：

- 文件保留原位置；
- 目录或单独文件注册为来源；
- 目录默认监听后续增减；
- 导入到播放列表时建立来源绑定；
- 不复制普通音频文件；
- NCM 可在约定子目录生成可播放衍生文件，但不覆盖或删除原文件。

托管模式：

- 文件复制到资料库内部；
- 原始目录不持续监听；
- 外部文件后续移动或删除不影响托管副本；
- 保持现有导入、播放和删除语义；
- 只修复重复、错误目标和生命周期缺陷。

### 7.5 导入结果必须可见

导入结果至少区分：

- 新增歌曲；
- 复用已有歌曲；
- 新加入播放列表；
- 已经在播放列表；
- 可能重复、未自动合并；
- 等待 NCM 转换；
- 失败及原因。

当已有 `1–10.mp3`，目录后来增加到 `1–15.mp3`，再导入到播放列表时，两种模式都必须得到：

- 新增歌曲 5；
- 复用已有歌曲 10；
- 播放列表最终 15；
- 所有歌曲最终 15；
- 不产生重复 Track 或重复托管副本。

## 8. 播放列表与来源同步

### 8.1 多对多绑定

- 一个目录可绑定多个播放列表；
- 一个播放列表可绑定多个目录；
- 同一目录重复绑定到同一播放列表必须幂等；
- 删除播放列表只删除绑定，不删除来源；
- 删除来源只移除该来源贡献的位置和成员关系，不删除其他来源或手动成员；
- 删除播放列表后，扫描不得重新创建它。

### 8.2 成员来源

播放列表每个成员记录：

- 手动加入标记；
- 一个或多个来源绑定 ID；
- 加入时间；
- 手动顺序；
- 针对某个来源绑定的排除状态。

歌曲只要仍有手动标记或至少一个来源绑定，就继续留在播放列表。

### 8.3 排序规则

- 播放列表保存用户手动顺序。
- 首次绑定目录时，来源歌曲按稳定相对路径顺序加入。
- 后续新增文件追加到绑定歌曲区域，不重排已有手动顺序。
- 视图层可以临时按标题、艺人、专辑等排序，但不因此覆盖持久手动顺序。
- 用户从来源绑定贡献的播放列表中手动移除歌曲时，写入绑定级排除项，避免下一次扫描立即复活。

### 8.4 未来配置预留

当前目录来源默认监听。模型中可以为绑定预留 `inherit/on/off` 监控策略及过滤条件，但当前 UI 不提供复杂配置，也不实现 MCP。

## 9. 核心领域模型

### 9.1 TrackRecord：逻辑歌曲

TrackRecord 表示资料库中的一首逻辑歌曲，不等同于一个文件路径。至少包含：

- 稳定 UUID；
- 有效展示元数据；
- 原始内嵌标签快照引用；
- 用户手动修正；
- 可选外部身份，例如 MBID 或 QQ Music MID；
- 添加和导入时间；
- 歌词、封面和用户描述引用；
- 播放统计引用；
- 一个或多个 TrackLocation。

### 9.2 TrackLocation：物理可播放位置

一个 TrackRecord 可对应多个位置。TrackLocation 至少包含：

- location ID；
- managed 或 referenced 类型；
- source ID 和相对路径，或托管相对路径；
- security-scoped bookmark；
- 文件系统稳定身份；
- 文件大小、修改时间和按需内容摘要；
- 可用状态；
- 格式、码率、采样率、位深和声道；
- NCM 原始资产或可播放衍生资产角色。

播放解析器从可用位置中选择最佳位置。一个来源离线时可以回退到另一位置。Track 不再只持有一个主要路径并假定它永远有效。

### 9.3 LibrarySource

LibrarySource 至少包含：

- 来源 ID；
- 目录或单文件模式；
- bookmark 和最后已知路径；
- 显示名；
- 可用状态；
- 创建时间和最后成功扫描时间；
- 监听策略；
- 扫描 generation；
- 扫描规则和清单引用。

来源与播放列表之间不保存单一 `playlistID`。

### 9.4 PlaylistSourceBinding

绑定至少包含：

- binding ID；
- source ID；
- playlist ID；
- 可选相对子目录；
- 创建时间；
- 当前监听策略；
- 绑定级排除项引用。

### 9.5 PlaylistMembership

成员至少包含：

- playlist ID；
- track ID；
- 手动加入标记；
- 来源 binding ID 集合；
- 首次和最近加入时间；
- 手动顺序；
- 排除/恢复信息。

当前简单的 `[Track]` 关系可作为运行时投影，但权威 sidecar 必须能表达来源和顺序。

## 10. 标签、艺人与专辑模型

### 10.1 元数据分层

每首歌的元数据拆成：

1. `EmbeddedMetadataSnapshot`：文件实际标签。
2. `UserMetadataOverride`：用户在 APP 中确认的修正。
3. `EnrichmentSuggestion`：在线候选和自动结果。
4. `EffectiveMetadata`：最终展示投影。

优先级为用户修正、文件标签、可信补全、文件名兜底。在线结果不得在无记录的情况下覆盖用户修改。

### 10.2 多艺人

引入 TrackCredit，至少支持：

- primary artist；
- featured artist；
- album artist。

后续可以扩展 composer、remixer 等角色。

解析规则：

- 优先读取原生多值标签；
- 始终保留原始展示字符串；
- `feat.`/`ft.` 可以形成参与艺人 credit；
- `&`、`+`、`/` 不能无条件拆分；
- 用户纠正和例外规则属于权威数据；
- 旧 Track 的单一 artist 字符串迁移为一个 primary credit，并保留原显示。

### 10.3 专辑身份

专辑身份优先级：

1. MusicBrainz Release ID；
2. 规范化专辑名 + Album Artist + 发行年份或版本提示；
3. 标签不足时，以来源文件夹作为辅助线索。

不能只按专辑名分组，也不能把曲目数作为稳定身份。曲目数会在增量扫描中变化，只适合作为审查信号。

### 10.4 合辑

- 优先读取 COMPILATION 标记；
- Album Artist 为 Various Artists 时按合辑展示；
- 缺少显式标记时可根据同目录、同专辑名、不同曲目艺人生成建议；
- 推断不自动写回文件；
- 合辑中的曲目艺人仍各自保留。

### 10.5 标签缺失

- 缺少艺人统一显示“未知艺人”；
- 缺少专辑的歌曲进入“未归类歌曲”，不制造大量假专辑；
- 文件夹视图始终保留真实位置，作为标签缺失时的兜底；
- 标签补全后只更新受影响投影，不改变来源、播放列表和 Track 身份。

### 10.6 标签写回

标签写回不是核心模型迁移的前置条件。后续实现时必须：

- 与 APP 内手动覆盖分开；
- 显式触发并展示变更预览；
- 原位文件重新确认权限；
- 批量操作提供进度和失败清单；
- 写回成功后触发受影响的索引和投影重算；
- 不把标签写回和移动文件合成同一个不可恢复操作。

## 11. 重复识别与文件身份

统一身份解析器按以下顺序工作：

1. 当前文件系统稳定身份；
2. 已知 NCM 原文件与转换输出关联；
3. 已保存物理 fingerprint；
4. 必要时计算内容摘要；
5. 标题、艺人、专辑和时长相似度只产生“可能重复”建议。

完整内容摘要按需计算，不在首次扫描时给全库所有文件无条件计算。

必须覆盖：

- 同一路径重复导入；
- 文件重命名或在同卷移动；
- 跨卷复制；
- Finder alias、符号链接和硬链接；
- 同一物理歌曲位于重叠来源；
- 元数据相同但录音不同；
- 同一 Track 的多个可播放位置；
- 托管模式同一输入源重复导入；
- 原位模式目录扩充后再次导入到播放列表。

## 12. 扫描、监听和重新扫描

### 12.1 原位模式

区分三个明确动作：

- **自动同步**：FSEvents 触发的增量同步；
- **重新扫描此来源**：只扫描选中的来源；
- **完整扫描全部来源**：用户主动发起全量核对。

来源状态展示：

- 最后成功扫描时间；
- 文件数量；
- 新增、移除和失败数量；
- 监听状态；
- 绑定的播放列表；
- 可用、离线、权限失效或需要重连。

扫描器只生成 immutable diff。reconciler 负责事务提交，FSEvents callback 不直接修改 Track。

### 12.2 托管模式

托管资料库不使用“重新扫描来源”文案。如保留维护入口，应称为“检查资料库完整性”，只核对：

- 托管音频；
- sidecar；
- 播放列表；
- 可重建索引。

它不扫描任意外部目录，也不重新导入原始路径。

### 12.3 删除与失效判定

- 来源离线：不删除。
- 权限失效：不删除，要求重连。
- 部分扫描失败：不删除。
- 事件风暴或扫描取消：不删除。
- 完整成功扫描确认文件不存在：移除该 TrackLocation。
- 仍有其他位置：Track 保留并继续播放。
- 没有位置：进入设置中的失效项目。

设置中的清理操作必须将真正缺失与临时离线、权限失效分开，不能一键删除后两者的元数据。

## 13. NCM 资产和播放可用性

NCM 采用“原始资产 + 可播放衍生资产”模型：

```text
NCM 原文件位置
  └── 转换任务
       └── MP3/FLAC 可播放衍生位置
```

规则：

- NCM 原文件是身份来源；
- 转换输出不是新的普通来源歌曲；
- 已有有效输出立即复用，Track 提交后即可播放；
- 只转换输出缺失、损坏或原文件 fingerprint 已变化的 NCM；
- 转换失败不阻塞其他文件导入；
- APP 退出后任务可以恢复或明确重试；
- 信息补全不决定播放可用性；
- 用户移除 NCM 时，ignore/tombstone 同时覆盖原文件和衍生输出，防止自动复活。

## 14. 后台任务与 Session 生命周期

每个 LibrarySession 拥有独立的 LibraryOperationCoordinator，统一管理：

- 导入计划和提交；
- 来源扫描与 reconcile；
- FSEvents 脏来源批次；
- NCM 转换；
- 信息补全；
- 搜索和浏览投影更新。

任务状态至少包括 queued、running、checkpointed、completed、partialFailure、failed 和 cancelled。

要求：

- 同一资料库的导入请求排队或合并，不静默丢弃；
- 任务捕获 library ID 和 generation；
- 旧 generation 结果不得写入新 Session；
- 切换前短事务完成提交或回滚；
- 长任务保存检查点后暂停或取消；
- quiesce 等待数据库、搜索索引和文件句柄真正释放；
- 不允许未登记的 detached task 在 Session 关闭后继续写盘；
- UI 通过可观察任务状态更新，不使用永久 250ms 轮询维持进度。

创建弹窗只等待“资料库最小结构已持久化并成功激活”，不等待初始扫描、NCM 或补全。

## 15. 持久化与迁移

### 15.1 权威数据

继续使用资料库文件和 sidecar 作为权威数据，SwiftData 和搜索 SQLite 是可重建投影。新模型至少需要持久化：

- TrackRecord 和多个 TrackLocation；
- 原始、用户和有效元数据层；
- LibrarySource；
- PlaylistSourceBinding；
- 带来源的 PlaylistMembership；
- NCM 原始/衍生关联；
- 忽略项和恢复记录。

### 15.2 托管资料库兼容要求

- 保留所有既有 Track UUID、播放列表 UUID 和播放顺序；
- 旧 managed locator 迁移为一个 managed TrackLocation；
- 不重新复制现有音频；
- 不读取或重新绑定旧 originalFilePath 作为持续来源；
- 不改变现有删除原理；
- 旧资料库无需用户重新导入即可打开和播放；
- 迁移后的托管库仍可被旧数据恢复工具识别，至少保留一个版本的兼容投影或迁移备份。

### 15.3 原位资料库迁移要求

- 旧 referenced locator 的 source memberships 迁移为 TrackLocation/来源关系；
- 旧来源的单一 `playlistID` 迁移成 PlaylistSourceBinding；
- `playlistManagedTrackIDs` 迁移成成员来源；
- 旧播放列表普通成员默认视为手动成员，除非有可靠来源证据；
- 单一 bookmark/lastKnownPath 迁移后不能丢失；
- NCM registry 与已有 Track 关联必须保留；
- 删除过的播放列表不能因旧来源描述再次创建。

### 15.4 艺人与专辑迁移要求

- 旧 artist 字符串先生成一个 primary credit，并保留原显示值；
- 旧 albumArtist 迁移为专辑艺人 credit；
- 旧 albumGroupKey 仅作为迁移线索，新专辑投影可重建；
- 不在迁移阶段自动拆分含 `&/+` 的艺人；
- 不在迁移阶段自动写回文件标签。

### 15.5 事务与回滚

- 升级前备份 library manifest、Track sidecar、来源、播放列表和 NCM registry；
- 使用持久化 migration journal；
- 每个阶段可重复执行；
- 完成后验证 Track 数、位置数、播放列表顺序、来源和索引完整性；
- 验证通过后再发布新 schema；
- 失败时保持旧资料库数据，不发布半迁移状态；
- 原位迁移绝不修改外部音频文件。

## 16. 服务边界

建议形成以下明确 owner。命名可在实现前按现有代码风格调整，但职责不能重新混合。

### LibraryLifecycleCoordinator

负责创建、打开、切换、删除、默认空库和 registry 事务。它不执行长时间扫描和补全。

### LibraryOperationCoordinator

每个 Session 一个，拥有导入、扫描、NCM、补全和索引任务及其 quiesce/close。

### ImportPlanner / ImportCommitter

Planner 展开输入、识别来源、确定身份和结果分类；Committer 原子提交 Track、位置、来源、播放列表成员和索引 intent。

### TrackIdentityResolver

统一 managed、referenced、NCM、文件移动、重复位置和内容摘要规则。UI 和 scanner 不自行实现第二套去重。

### SourceCatalog / SourceReconciler

SourceCatalog 管理来源与授权；scanner 产生 diff；reconciler 批量提交 TrackLocation 和播放列表绑定变化。

### LibraryCommandService / LibraryQueryService

UI 使用命令服务修改资料库，使用查询服务读取歌曲、文件夹、来源、绑定和任务状态。未来 MCP 可以复用同一命令和查询边界，但本轮不实现 MCP adapter。

## 17. 搜索、性能与大资料库

### 17.1 搜索字段

搜索逐步扩展到：

- 标题；
- 主艺人和参与艺人；
- Album Artist；
- 专辑；
- 文件名；
- 来源和相对路径；
- 流派、年份和格式；
- 歌词纯文本。

### 17.2 性能要求

- 文件发现、标签读取和内容摘要分阶段执行；
- 首次扫描先提交可播放的最小 Track，再补充增强数据；
- 内容摘要仅在身份歧义时按需计算；
- 来源 manifest 支持增量扫描；
- 专辑、艺人、文件夹和搜索投影增量更新；
- 列表使用分页、虚拟化或稳定快照，不要求把全部 Track、封面和歌词长期装入主线程内存；
- 扫描事件合并后提交，避免每个文件变更触发一次完整 reload；
- 大库压力验证至少覆盖 10 万条元数据索引，同时用真实音频子集验证播放和标签读取。

## 18. 设置页面调整

### 18.1 资料库设置

保留：

- 新建和打开资料库；
- 当前资料库、模式和存储路径；
- 原位来源列表；
- 来源重新连接；
- 重新扫描此来源；
- 原位库完整扫描全部来源；
- 从 APP 移除资料库。

隐藏或修正：

- 隐藏“更改位置”；
- 当前只 reload UI 的资料库“重新扫描”不得保留原文案；
- 单来源扫描不得实际扫描全部来源；
- “在 Finder 中显示”先验证当前已解析路径；
- 删除无行为或不可达的“重新连接”按钮分支。

### 18.2 数据设置

放置：

- 失效项目；
- 临时离线来源；
- 权限失效来源；
- 可重建索引维护；
- 缓存清理；
- 后续重复歌曲审查。

真正缺失、磁盘离线和权限失效必须分组，不能用一个“一键清空失效歌曲”混合处理。

## 19. 分阶段实施计划

每个阶段必须独立完成、审查和验收，不允许为了赶进度跨阶段堆叠半成品。后续 Agent 开始工作前先阅读本文、`docs/architecture.md` 和 `docs/library-storage.md`，记录 branch、HEAD 和 dirty baseline，并保留无关用户改动。

阶段按 `0 → 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8` 顺序推进。领域模型和导入事务完成前不提前落文件夹 UI；来源绑定完成前不在 UI 中伪造关系；艺人/专辑迁移不得与来源 schema 迁移并行修改同一批 Track sidecar。维护者可以把单阶段拆成多个小任务，但只有该阶段所有退出条件满足后才能进入下一阶段。

### 阶段 0：冻结错误入口和建立行为基线

目标：停止继续暴露已确认错误，不改变资料库 schema。

任务：

- 隐藏“更改位置”；
- 隐藏或正确重命名假的资料库“重新扫描”；
- 禁用会混删离线/权限项目的危险清理；
- 移除无行为的设置按钮分支；
- 建立入口审计表：按钮 → command → service → 持久化 → UI 结果；
- 固定托管和原位现有样本资料库，保存迁移前基线；
- 为后续手动验收准备隔离的测试音乐目录，不使用用户真实资料库做破坏性验证。

退出条件：

- 设置中没有已知假按钮和危险入口；
- 托管资料库打开、播放、导入和删除行为有可复现基线；
- 原位资料库来源、播放列表和 NCM 样本状态有可复现基线。

### 阶段 1：修复资料库创建和生命周期

目标：先让资料库总能正确创建、关闭、激活、切换和兜底。

任务：

- 普通新建强制选择存储位置；
- 冲突提示显示具体路径；
- 删除隐式默认路径和静默编号目录行为；
- 修正新建原位资料库的选项，不显示“绑定已有播放列表”；
- 将最小资料库创建与初始导入拆开；
- 创建成功后立即关闭向导；
- 统一 setup panel 的唯一窗口状态 owner 和幂等关闭路径；
- 删除当前资料库后切换到其他可达资料库；
- 没有可达资料库时创建默认空库；
- 空库显示“没有歌曲待导入”；
- 建立 LibraryOperationCoordinator 的最小任务 ownership 和 Session quiesce 协议。

退出条件：

- 未选择位置不能创建；
- 创建、取消和关闭无残留空壳 panel；
- 初始补全失败不阻塞弹窗关闭；
- 删除唯一资料库后自动进入默认空库；
- 退出重开不会进入无资料库空窗口；
- 切库后旧任务不写入新库。

### 阶段 2：升级持久化领域模型

目标：建立 TrackLocation、来源绑定和成员来源，为原位重构提供可靠基础。

任务：

- 增加 TrackRecord/TrackLocation 持久化表达；
- 增加 PlaylistSourceBinding；
- 增加带来源的 PlaylistMembership；
- 来源 schema 删除单一 playlist owner 语义；
- 引入迁移 journal、备份、验证和回滚；
- 迁移托管资料库单一 managed locator；
- 迁移原位 source memberships、playlistID 和 managed IDs；
- 保留 Track/Playlist UUID 和播放列表顺序；
- 更新 locator resolver，支持多位置选择和回退；
- 暂时保留必要兼容投影，避免一次性改穿全部 UI。

退出条件：

- 旧托管资料库无需重新导入即可播放；
- 旧原位资料库来源和播放列表关系不丢失；
- 同一 Track 可拥有两个位置并在一个位置离线时回退；
- 删除播放列表后不会被来源扫描复活；
- 迁移失败可回滚且不修改外部音频。

### 阶段 3：统一导入事务和重复识别

目标：所有导入入口共享一个明确、幂等、可报告的事务模型。

任务：

- 引入 ImportContext、ImportDestination 和 metadataContext；
- Toolbar、菜单、窗口拖放统一捕获当前 UI 上下文；
- 播放列表页面导入到该播放列表；
- 首页和未定义上下文只导入所有歌曲；
- 艺人/专辑上下文只提供可见元数据预填，不创建播放列表；
- Sidebar 播放列表 drop 锁定目标并优先于窗口 drop；
- 删除自动选择第一个播放列表和自动创建 Imported 播放列表的逻辑；
- 建立 TrackIdentityResolver；
- managed/referenced/NCM 使用统一结果分类；
- 导入请求排队，不静默丢弃；
- 返回新增、复用、加入播放列表、已存在、疑似重复和失败明细。

退出条件：

- `1–10 → 1–15` 场景在两种模式都得到正确结果；
- 拖到所有歌曲不会创建播放列表；
- 拖到 Sidebar 播放列表只执行一次且目标固定；
- 文件选择器期间切页不会改变目标；
- 导入期间切库不会写错资料库；
- 托管资料库外部源不被错误注册为持续监听来源。

### 阶段 4：原位来源、绑定和目录监听重构

目标：完整实现原位资料库的来源所有权和播放列表同步。

任务：

- 来源注册、授权、扫描、监听和删除走 SourceCatalog；
- 目录拖入播放列表时创建或复用来源并建立 binding；
- 同一来源支持多个播放列表；
- 一个播放列表支持多个来源；
- 文件导入播放列表后同时进入所有歌曲和来源列表；
- scanner 只生成 diff，reconciler 负责批量事务；
- 多个脏来源一起 reconcile，处理跨来源移动；
- 自动监听目录增减；
- 实现绑定级排除和恢复；
- 单来源扫描真正定向；
- 完整扫描全部来源有明确结果；
- 来源离线、权限失效和部分失败不删除 Track；
- 删除来源只移除该来源贡献，保留其他位置和手动成员。

退出条件：

- 同一目录绑定两个播放列表后，新增歌曲同时出现；
- 删除一个播放列表不影响来源和另一个播放列表；
- 同一歌曲来自两个来源时只有一个 Track；
- 一个来源离线后可使用另一个位置播放；
- 手动从绑定播放列表移除后不会自动复活；
- 文件移动、目录改名和事件风暴不会造成重复或批量误删。

### 阶段 5：NCM 资产链路

目标：让 NCM 从导入开始即遵守标准身份、来源和播放可用性规则。

任务：

- 将 NCM 原文件和可播放输出表达为关联资产；
- 复用既有有效 MP3/FLAC；
- 只转换真正缺少或失效的输出；
- 转换输出不被来源扫描当成第二首普通歌曲；
- Track 只有在拥有有效可播放位置时标记可播放；
- 转换任务进入 LibraryOperationCoordinator；
- 中断、退出、切库和重启可恢复；
- ignore/removal 同时处理原文件和输出。

退出条件：

- 已有输出的 NCM 导入后立即可播放；
- 混合“已转换 + 未转换”目录只转换缺失部分；
- 信息补全期间歌曲不变成不可用；
- APP 中途退出不留下重复输出或永久 pending；
- 输出损坏后能够定向重建。

### 阶段 6：文件夹视图和播放列表折叠 UI

目标：以克制、现代的 UI 展示来源、文件夹、歌曲和播放列表关系。

任务：

- 播放列表 Sidebar 分组可折叠并持久化状态；
- 原位资料库增加一个文件夹入口；
- 实现左侧来源/目录树和右侧关系/歌曲详情；
- 增加“单独添加的歌曲”分组；
- 显示目录与播放列表 binding；
- 支持建立和解除绑定；
- 支持来源状态、重新扫描、重连和 Finder 定位；
- 保留选择、滚动和展开状态；
- 使用现有主题、材质、行组件和工具栏体系；
- 对大目录使用虚拟化或分页；
- 托管资料库 UI 保持现状，不展示内部 UUID 目录。

退出条件：

- 用户无需进入设置即可理解“这个目录属于哪些播放列表”；
- 解除关系不会删除来源或歌曲；
- 扫描更新不重置目录树位置；
- 离线与权限状态清晰但不干扰正常浏览；
- 拖放高亮和实际目标一致；
- UI 与现有 APP 风格一致，不形成独立文件管理器风格。

### 阶段 7：艺人、专辑和元数据模型升级

目标：对标成熟本地播放器的 Album Artist、多艺人、合辑和标签缺失行为。

任务：

- 增加 TrackCredit 和多值艺人；
- Album Artist 成为一等字段；
- 增加合辑身份和 Various Artists 投影；
- 重建专辑身份规则；
- 迁移旧 artist/albumArtist 数据；
- 未知艺人与未归类歌曲使用稳定兜底；
- 更新艺人、专辑、首页、搜索、Now Playing 和编辑 UI；
- 搜索加入参与艺人、Album Artist、文件名和路径；
- 元数据补全写入 suggestion/effective 层，不覆盖用户层；
- 保留原 artist 显示字符串，避免错误拆分。

退出条件：

- 多艺人歌曲出现在各正确艺人下且不制造组合艺人垃圾条目；
- 合辑只形成一个正确专辑；
- 同名专辑由 Album Artist/版本信息区分；
- 标签缺失不破坏文件夹浏览；
- 修改标签只更新受影响投影，不改变 Track、来源和播放列表身份。

### 阶段 8：本地增强、性能与完整验收

目标：在核心稳定后补足本地管理能力，并完成发布前系统验收。

候选任务按优先级逐项实施：

- 批量标签编辑和显式写回；
- 智能集合；
- 品质和格式统计；
- 重复歌曲审查；
- 来源过滤和排除目录；
- 搜索字段与排序扩展；
- 10 万级索引、内存和增量扫描优化。

退出条件：

- 所有核心真实场景和故障注入完成；
- 大库浏览、搜索和扫描无明显主线程阻塞；
- 数据设置能区分缺失、离线和权限问题；
- 托管旧资料库兼容矩阵通过；
- 原位资料库的来源、绑定、播放和恢复行为通过人工验收。

## 20. 验证策略

测试是证据之一，不是完成定义。每个阶段同时要求静态、集成、真实 UI 和故障证据。

### 20.1 行为审计

维护一张入口矩阵：

```text
用户入口
  → 捕获的 library/generation/selection
  → command
  → service owner
  → 权威文件变化
  → 索引变化
  → UI 结果或错误
```

没有完整链路的按钮不得进入产品 UI。

### 20.2 真实目录集成验证

- 使用隔离临时资料库和真实音频 fixture；
- scanner、repository、sidecar 和 monitor 尽量使用真实实现；
- 验证来源描述、TrackLocation、binding、播放列表 sidecar 和 registry；
- 所有后台任务和数据库句柄结束后才能删除临时目录；
- 测试清理期间出现 SQLite 文件仍被访问，视为生命周期失败，不能忽略。

### 20.3 Finder 与真实 APP 验证

至少覆盖：

- 在明确位置创建资料库；
- 取消位置选择；
- 创建冲突；
- 新建空库；
- Toolbar 导入；
- 窗口普通区域拖放；
- Sidebar 播放列表拖放；
- 目录新增、删除、重命名和移动；
- 同一目录绑定两个播放列表；
- 外置磁盘断开和重新挂载；
- 权限撤回和重连；
- 切库、删除当前库、退出和重启；
- NCM 复用、转换、损坏和中断。

### 20.4 故障注入

- 资料库目录只读；
- 磁盘空间不足；
- bookmark 过期；
- 部分目录不可读；
- 扫描中退出；
- 导入中切换资料库；
- NCM 转换中退出；
- sidecar 写入成功但索引更新失败；
- APP 在迁移 stage/commit 之间崩溃。

### 20.5 托管兼容矩阵

至少保留以下旧资料库 fixture：

- 只有普通音频；
- 带播放列表、歌词和封面；
- 带旧 locator/bookmark；
- 带播放历史和偏好统计；
- 含 NCM 导入结果；
- 有缺失托管文件或损坏索引。

每次领域模型和迁移改动都必须重新验证这些 fixture，不得只验证新建资料库。

## 21. Agent 交接规范

后续 Agent 每次只领取一个实施阶段或其中一个明确子任务。

开始前：

1. 确认工作树是 `feature/multi-library-storage`；
2. 记录 HEAD 和 `git status --short`；
3. 阅读本文及直接相关架构文档；
4. 使用 CodeGraph 定位当前调用链；
5. 区分用户已有改动和本任务改动；
6. 写明本阶段不处理的边界。

实施中：

- 先修改领域命令和 owner，再接 UI；
- 不在 SwiftUI 中创建第二套资料库服务；
- 不在 FSEvents callback 直接写 Track；
- 不在多个入口分别实现去重；
- 不用修改托管行为来简化原位实现；
- 不修改外部真实音乐文件做自动化验证；
- 不把未来 MCP/Navidrome 代码混入当前阶段。

交付时必须说明：

- 完成了本文哪一阶段、哪些条目；
- 修改了哪些权威数据和迁移；
- 已验证哪些真实行为；
- 未验证哪些硬件、磁盘或 UI 边界；
- 是否启动了新 APP 供维护者测试；
- 是否存在需要下一 Agent 接手的已知阻塞。

只有编译通过、单元测试通过或 mock 数量断言通过，均不能单独标记阶段完成。

## 22. 最终完成定义

本地音乐资料库重构完成时，用户应当获得以下稳定体验：

- APP 永远有一个可用资料库，至少是默认空库；
- 原位资料库是新建时首推模式；
- 托管旧资料库不需要重新导入，行为不被破坏；
- 所有导入入口的目标都可预测；
- 播放列表目录拖放、复用已有歌曲和自动监听可靠；
- 所有歌曲、来源、文件夹和播放列表关系一致；
- 同一歌曲可有多个位置而不重复显示；
- NCM 已有转换结果立即可播放；
- 标签、Album Artist、多艺人和合辑模型达到成熟本地播放器的基本水平；
- 主侧边栏仍然简洁，播放列表可收起，文件夹关系在窗口内清晰呈现；
- 失效、离线和权限问题在设置中有明确恢复路径；
- 创建、扫描、导入、补全、切库和关闭没有卡死弹窗或后台越库写入；
- 未来 MCP 和 Navidrome 可以复用命令、查询、身份和播放资源边界，而无需重写本地资料库。
